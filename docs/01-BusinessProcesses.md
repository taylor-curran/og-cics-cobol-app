# Business Processes & Scope

## 1. Introduction

### 1.1 Document Purpose
This document captures the business processes and operational scope of the CICS Bank Sample Application (CBSA) to serve as requirements input for modernization to a Java-based technology stack. It describes the existing teller operations, customer management workflows, account operations, and financial transaction processes currently implemented in the COBOL/CICS/BMS system.

**Source**: Based on analysis of `README.md`, `doc/CBSA_Architecture_guide.md`, and `etc/usage/base/doc/CBSA_BMS_User_Guide.md`

### 1.2 Application Overview
CBSA is a multi-interface banking application that simulates bank operations from a teller's perspective. The application provides:
- **Core Banking Functions**: Customer and account management, financial transactions
- **Multiple Access Channels**: 3270 BMS terminal interface, Carbon React web UI, RESTful API services
- **Data Management**: Db2 relational tables (ACCOUNT, PROCTRAN, CONTROL) and VSAM files (CUSTOMER)
- **Transaction Logging**: Comprehensive audit trail in PROCTRAN table

**Current Technology Stack**: COBOL, CICS, BMS maps, Db2, VSAM, Liberty JVM Server, Spring Boot, z/OS Connect

### 1.3 Scope of Operations
The application supports the following operational domains:
1. Customer lifecycle management (create, inquire, update, delete)
2. Account lifecycle management (create, inquire, update, delete)
3. Financial transactions (debit, credit, transfer)
4. Customer-account relationship management
5. Transaction audit and compliance logging

## 3. Customer Management Processes

### 3.1 Create Customer (Option 3)

#### 3.1.1 Business Process Flow
1. Teller selects option 3 from main menu
2. System displays customer creation form (BMS map BNK1CCM)
3. Teller enters customer details:
   - Title (validated against approved list)
   - Full name
   - Street address
   - Town/city
   - Postcode/ZIP
   - Date of birth (DD/MM/YYYY format)
4. System validates input data
5. System generates unique customer number via Named Counter (CBSACUST)
6. System initiates asynchronous credit checks with multiple agencies
7. System aggregates credit scores
8. System writes customer record to CUSTOMER VSAM file
9. System logs transaction in PROCTRAN Db2 table (type='OCC' for branch create)
10. System displays confirmation with new customer number

**Source**: Program `CRECUST.cbl` (lines 9-34), `BNK1CCS.cbl`, Map `BNK1CCM.bms`

#### 3.1.2 Business Rules
- **Title Validation**: Must be one of: Professor, Mr, Mrs, Miss, Ms, Dr, Drs, Lord, Sir, Lady
- **Date of Birth Validation**:
  - Year must be >= 1601 (CEEDAYS minimum)
  - Age must be <= 150 years (business rule)
  - Date cannot be in the future
- **Credit Check**: Async calls to 3-5 credit agencies (CRDTAGY1-5), wait up to 3 seconds, aggregate/average scores
- **Customer Number**: 10-digit unique number generated by Named Counter CBSACUST
- **Sort Code**: System-defined value (from SORTCODE copybook)

**Source**: `CRECUST.cbl` (lines 91-203 for DOB validation, lines 205-387 for credit check logic)

#### 3.1.3 Validation Error Codes
| Code | Meaning | Source |
|------|---------|--------|
| '1' | Customer number generation failed | CRECUST.cbl line 142 |
| 'O' | Date of birth year/age violation | CRECUST.cbl line 199 |
| 'Y' | Date of birth is in future | CRECUST.cbl line 193 |
| 'G' | Credit check agency error | CRECUST.cbl line 340 |
| '2' | VSAM write failure | CRECUST.cbl line 370 |
| '3' | PROCTRAN logging failure | CRECUST.cbl line 384 |

#### 3.1.4 Acceptance Criteria
- **AC1**: Given valid customer details with DOB >= 1601 and age <= 150, When create customer is submitted, Then system generates unique customer number and stores record
- **AC2**: Given customer with valid DOB, When credit checks complete, Then system aggregates scores from all responding agencies
- **AC3**: Given successful customer creation, When transaction completes, Then PROCTRAN contains log entry with type 'OCC'
- **AC4**: Given invalid title (not in approved list), When create customer is submitted, Then system rejects with appropriate error message
- **AC5**: Given DOB in future, When create customer is submitted, Then system returns fail code 'Y'

#### 3.1.5 Modernization Considerations
- **REST Endpoint**: `POST /api/customers`
- **Request Body**: JSON with name, address, dateOfBirth fields
- **Response**: HTTP 201 Created with customer object including generated ID
- **Credit Check**: Implement as async Spring @Async calls or event-driven with message queue
- **Validation**: Use Java Bean Validation annotations (@Past, @NotNull, etc.)
- **ID Generation**: Replace Named Counter with database sequence or UUID

### 3.2 Inquire Customer (Option 1)

#### 3.2.1 Business Process Flow
1. Teller selects option 1 from main menu
2. System displays customer inquiry form (BMS map BNK1DCM)
3. Teller enters customer number
4. System reads CUSTOMER VSAM file
5. System displays customer details (name, address, DOB, credit score)
6. Teller can then:
   - Press F5 to delete customer
   - Press F10 to update customer
   - Press F12 to cancel/return

**Source**: Program `INQCUST.cbl` (lines 9-19), `BNK1DCS.cbl`, Map `BNK1DCM.bms`

#### 3.2.2 Business Rules
- **Special Customer Numbers**:
  - `0000000000`: Returns random customer from file
  - `9999999999`: Returns last customer added (via Named Counter query)
- **Not Found**: Returns record with low-values and fail code '1'
- **SYSIDERR Retry**: If VSAM read fails with SYSIDERR, retry up to 100 times with 3-second delays

**Source**: `INQCUST.cbl` (lines 154-275 for special number handling, lines 321-400 for retry logic)

#### 3.2.3 Acceptance Criteria
- **AC1**: Given valid customer number, When inquiry is submitted, Then system returns complete customer record
- **AC2**: Given customer number 0000000000, When inquiry is submitted, Then system returns random customer
- **AC3**: Given customer number 9999999999, When inquiry is submitted, Then system returns most recently created customer
- **AC4**: Given non-existent customer number, When inquiry is submitted, Then system returns fail code '1'

#### 3.2.4 Modernization Considerations
- **REST Endpoint**: `GET /api/customers/{customerId}`
- **Response**: HTTP 200 OK with customer JSON, or HTTP 404 Not Found
- **Special IDs**: Consider removing random/last customer features or implement as separate endpoints
- **Retry Logic**: Implement with Spring Retry or Resilience4j

### 3.4 Delete Customer (Option 1 → F5)

#### 3.4.1 Business Process Flow
1. From customer inquiry screen, teller presses F5
2. System validates customer has no associated accounts
3. System deletes CUSTOMER VSAM record
4. System logs transaction in PROCTRAN with type='ODC'
5. System displays confirmation

**Source**: Program `DELCUS.cbl`, `BNK1DCS.cbl`

#### 3.4.2 Business Rules
- **Account Check**: Cannot delete customer with existing accounts
- **Transaction Logging**: Writes to PROCTRAN with customer details
- **Irreversible**: No soft delete; record is physically removed

**Source**: `DELCUS.cbl` (referenced in BANK.csd lines 202-207)

#### 3.4.3 Acceptance Criteria
- **AC1**: Given customer with no accounts, When delete is requested, Then system deletes customer and logs to PROCTRAN
- **AC2**: Given customer with active accounts, When delete is requested, Then system rejects with appropriate error
- **AC3**: Given successful deletion, When transaction completes, Then PROCTRAN contains entry with type 'ODC'

#### 3.4.4 Modernization Considerations
- **REST Endpoint**: `DELETE /api/customers/{customerId}`
- **Response**: HTTP 204 No Content on success, HTTP 409 Conflict if customer has accounts
- **Soft Delete**: Consider implementing soft delete with deleted_at timestamp instead of physical deletion
- **Audit**: Transaction log should capture who/when/why for compliance

## 4. Account Operations Processes

### 4.1 Create Account (Option 4)

#### 4.1.1 Business Process Flow
1. Teller selects option 4 from main menu
2. System displays account creation form (BMS map BNK1CAM)
3. Teller enters:
   - Customer number (must exist)
   - Account type (CURRENT, SAVINGS, LOAN, MORTGAGE, ISA)
   - Interest rate
   - Overdraft limit
4. System validates customer exists via INQCUST
5. System checks customer doesn't exceed 9 accounts via INQACCCU
6. System generates unique account number via Named Counter (CBSAACCT)
7. System writes to ACCOUNT Db2 table
8. System logs transaction in PROCTRAN with type='OCA'
9. System displays confirmation with new account number

**Source**: Program `CREACC.cbl` (lines 9-22), `BNK1CAC.cbl`, Map `BNK1CAM.bms`

#### 4.1.2 Business Rules
- **Customer Validation**: Customer must exist (checked via INQCUST)
- **Account Limit**: Maximum 9 accounts per customer
- **Account Types**: CURRENT, SAVINGS, LOAN, MORTGAGE, ISA
- **Account Number**: 8-digit unique number from Named Counter CBSAACCT
- **Initial Balance**: Both available and actual balance start at 0.00
- **Statement Dates**: Last statement date = opened date, next statement date = opened date + 1 month
- **ENQ/DEQ**: Uses CICS resource locking for Named Counter access
- **Retry Logic**: If counter read fails, retries up to 3 times

**Source**: `CREACC.cbl` (lines 178-305 for customer validation, lines 447-683 for counter logic, lines 788-893 for account limit check)

#### 4.1.3 Validation Error Codes
| Code | Meaning | Source |
|------|---------|--------|
| '1' | Customer not found | CREACC.cbl line 245 |
| '2' | Customer inquiry failed | CREACC.cbl line 248 |
| '3' | ENQ on counter failed | CREACC.cbl line 510 |
| '4' | Counter read failed after retries | CREACC.cbl line 584 |
| '5' | Counter update failed | CREACC.cbl line 638 |
| '6' | ACCOUNT insert failed | CREACC.cbl line 959 |
| '7' | PROCTRAN insert failed | CREACC.cbl line 1060 |
| '8' | Customer has maximum 9 accounts | CREACC.cbl line 826 |
| '9' | Account count inquiry failed | CREACC.cbl line 829 |

#### 4.1.4 Acceptance Criteria
- **AC1**: Given valid customer and account details, When create account is submitted, Then system generates unique 8-digit account number
- **AC2**: Given customer with 9 existing accounts, When create account is submitted, Then system rejects with fail code '8'
- **AC3**: Given non-existent customer number, When create account is submitted, Then system rejects with fail code '1'
- **AC4**: Given valid account type, When account is created, Then both available and actual balance are 0.00
- **AC5**: Given successful account creation, When transaction completes, Then PROCTRAN contains entry with type 'OCA' and account details

#### 4.1.5 Modernization Considerations
- **REST Endpoint**: `POST /api/accounts`
- **Request Body**: JSON with customerId, accountType, interestRate, overdraftLimit
- **Response**: HTTP 201 Created with account object including generated accountNumber
- **ID Generation**: Replace Named Counter with database sequence
- **Validation**: Use enum for account types, validate interest rate and overdraft ranges
- **Concurrent Access**: Replace ENQ/DEQ with optimistic locking (@Version in JPA)

## 5. Financial Transaction Processes

### 5.1 Debit/Credit Funds (Option 6)

#### 5.1.1 Business Process Flow
1. Teller selects option 6 from main menu
2. System displays debit/credit form (BMS map BNK1CDM)
3. Teller enters:
   - Sort code and account number
   - Amount
   - Transaction type (Debit or Credit)
4. System validates account exists
5. For debit: System checks sufficient funds (actual balance + overdraft >= amount)
6. System updates account balances
7. System logs transaction in PROCTRAN (type='DEB' or 'CRE')
8. System displays confirmation with new balances

**Source**: Program `DBCRFUN.cbl` (lines 10-29), `BNK1CRA.cbl`, Map `BNK1CDM.bms`

#### 5.1.2 Business Rules
- **Debit Validation**: 
  - Actual balance + overdraft limit must be >= debit amount
  - Account type restrictions apply via Payment interface
- **Credit Validation**: No restrictions on credit amount
- **Balance Updates**:
  - For debit: actual_balance -= amount, available_balance -= amount
  - For credit: actual_balance += amount, available_balance += amount
- **Account Type Restrictions**: 
  - MORTGAGE and LOAN accounts cannot be debited/credited via Payment Services interface
  - This restriction is enforced at the interface layer, not in DBCRFUN itself
- **Transaction Logging**: All successful transactions logged to PROCTRAN

**Source**: `DBCRFUN.cbl` (lines 246-344 for debit logic, lines 390-458 for credit logic, lines 531-624 for PROCTRAN logging)

#### 5.1.3 Validation Error Codes
| Code | Meaning | Source |
|------|---------|--------|
| '1' | Account not found | DBCRFUN.cbl line 213 |
| '2' | Account update failed | DBCRFUN.cbl line 340 |
| '3' | Insufficient funds for debit | DBCRFUN.cbl line 285 |
| '4' | Invalid account type (via interface) | Interface layer |

#### 5.1.4 Acceptance Criteria
- **AC1**: Given valid account and credit amount, When credit is submitted, Then both balances increase by amount and PROCTRAN logged
- **AC2**: Given valid account with sufficient funds and debit amount, When debit is submitted, Then both balances decrease by amount and PROCTRAN logged
- **AC3**: Given debit amount exceeding available funds, When debit is submitted, Then system rejects with fail code '3'
- **AC4**: Given successful transaction, When operation completes, Then PROCTRAN contains entry with type 'DEB' or 'CRE', amount, and timestamp

#### 5.1.5 Modernization Considerations
- **REST Endpoint**: `POST /api/accounts/{accountId}/transactions`
- **Request Body**: JSON with type ('DEBIT' or 'CREDIT'), amount, description
- **Response**: HTTP 201 Created with transaction receipt including new balances
- **Validation**: Enforce business rules at service layer with clear exception types
- **Idempotency**: Consider idempotency key for duplicate prevention
- **Account Type Rules**: Implement as configurable business rules

### 5.2 Transfer Funds (Option 7)

#### 5.2.1 Business Process Flow
1. Teller selects option 7 from main menu
2. System displays transfer form (BMS map BNK1TFM)
3. Teller enters:
   - Source account (sort code + account number)
   - Destination account (sort code + account number)
   - Transfer amount
4. System validates both accounts exist
5. System validates source ≠ destination
6. System validates amount > 0
7. System validates sufficient funds in source account
8. System locks both accounts (lower account number first to prevent deadlock)
9. System debits source account
10. System credits destination account
11. System logs transaction in PROCTRAN (type='TFR') with cross-reference
12. On any failure after step 9: System issues SYNCPOINT ROLLBACK
13. System displays confirmation with updated balances for both accounts

**Source**: Program `XFRFUN.cbl` (lines 11-38), `BNK1TFN.cbl`, Map `BNK1TFM.bms`

#### 5.2.2 Business Rules
- **Same Account Check**: Source and destination accounts must be different
- **Amount Validation**: Transfer amount must be > 0
- **Sufficient Funds**: Source account actual_balance + overdraft_limit >= amount
- **Locking Strategy**: Acquire locks in account number order (lowest first) to prevent Db2 deadlocks
- **Atomic Operation**: Uses Db2 transaction with SYNCPOINT ROLLBACK on any failure
- **Transaction Logging**: Single PROCTRAN entry references both accounts
- **Overdraft**: Can transfer into overdraft if source account has overdraft limit
- **Retry Logic**: Includes deadlock retry mechanism (attempts Db2 access up to 10 times)

**Source**: `XFRFUN.cbl` (lines 486-676 for source debit, lines 726-898 for destination credit, lines 945-1127 for PROCTRAN, lines 1240-1335 for rollback logic)

#### 5.2.3 Validation Error Codes
| Code | Meaning | Source |
|------|---------|--------|
| '1' | Source account not found | XFRFUN.cbl line 353 |
| '2' | Destination account not found | XFRFUN.cbl line 417 |
| '3' | Source and destination are same account | XFRFUN.cbl line 298 |
| '4' | Transfer amount <= 0 | XFRFUN.cbl line 279 |
| '5' | Insufficient funds in source account | XFRFUN.cbl line 646 |
| '6' | Source debit update failed | XFRFUN.cbl line 670 |
| '7' | Destination credit update failed | XFRFUN.cbl line 892 |
| '8' | PROCTRAN logging failed | XFRFUN.cbl line 1121 |

#### 5.2.4 Acceptance Criteria
- **AC1**: Given valid source and destination accounts with sufficient funds and amount > 0, When transfer is submitted, Then source is debited, destination is credited, and PROCTRAN logged with type 'TFR'
- **AC2**: Given same account for source and destination, When transfer is submitted, Then system rejects with fail code '3'
- **AC3**: Given transfer amount <= 0, When transfer is submitted, Then system rejects with fail code '4'
- **AC4**: Given insufficient funds in source account, When transfer is submitted, Then system rejects with fail code '5'
- **AC5**: Given destination credit fails after source debit, When failure occurs, Then system issues SYNCPOINT ROLLBACK and source balance unchanged
- **AC6**: Given successful transfer, When operation completes, Then PROCTRAN entry includes description with destination account details

#### 5.2.5 Modernization Considerations
- **REST Endpoint**: `POST /api/transfers`
- **Request Body**: JSON with fromAccountId, toAccountId, amount, description
- **Response**: HTTP 201 Created with transfer receipt including updated balances for both accounts
- **Transaction Management**: Use Spring @Transactional with proper isolation level
- **Deadlock Prevention**: Implement similar ordered locking or rely on database retry
- **Idempotency**: Critical for transfers; consider idempotency key or deduplication
- **Async Processing**: Consider async for large/complex transfers with status tracking
- **Notification**: Add event publishing for downstream notifications

## 6. Cross-Functional Requirements

### 6.1 Transaction Audit Trail
All successful write operations (create, delete, debit, credit, transfer) are logged to the PROCTRAN Db2 table. This provides:
- Compliance audit trail
- Transaction history for customer inquiries
- Reconciliation capabilities
- Dispute resolution evidence

**Source**: `src/base/cobol_copy/PROCTRAN.cpy`

**Transaction Types Logged**:
| Type | Description | Source Program |
|------|-------------|----------------|
| OCC | Branch Create Customer | CRECUST |
| ODC | Branch Delete Customer | DELCUS |
| OCA | Branch Create Account | CREACC |
| ODA | Branch Delete Account | DELACC |
| DEB | Debit transaction | DBCRFUN |
| CRE | Credit transaction | DBCRFUN |
| TFR | Transfer between accounts | XFRFUN |
| ICC | Web Create Customer | CRECUST (API) |

| ICA | Web Create Account | CREACC (API) |
| IDA | Web Delete Account | DELACC (API) |

| PDR | Payment Debit | DBCRFUN (Payment API) |

**Modernization**: Implement comprehensive audit logging with user identity, IP address, and request correlation IDs.

### 6.2 Error Handling and Recovery
All programs follow a consistent error handling pattern:
- Invoke ABNDPROC for unrecoverable errors
- Write error details to ABNDFILE VSAM
- Return fail codes to caller for recoverable errors
- Use CICS HANDLE ABEND for CICS errors
- Implement storm drain processing for Db2 errors

**Source**: Multiple programs reference `ABNDPROC.cbl` and `ABNDFILE`

**Modernization**: Implement centralized exception handling with proper HTTP status codes and error response structure.

### 6.3 Data Consistency
- **Named Counters**: Use CICS ENQ/DEQ for serialized access to counter resources
- **Db2 Transactions**: Explicit SYNCPOINT ROLLBACK on errors
- **VSAM Locking**: Record-level locking for UPDATE operations
- **Retry Mechanisms**: Implement retry logic for transient errors (SYSIDERR, Db2 deadlocks)

**Modernization**: Use database transactions, optimistic locking, and distributed transaction coordination where needed.
